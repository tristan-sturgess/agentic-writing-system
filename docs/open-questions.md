1. **This repository is the build.** The Linear project text described itself as architecture-only. Implementation follows these docs.
2. **The build order is the Story Bible, then light editing and visualization, then an arc-planning chat agent, then evaluations, then prose.** Prose stays out until then.
3. **Railway is the hosted target, after a local-first implementation.** Each story has an owner.
4. **Story Space stays out of the first slices.** Location entities can exist in the bible. The location agent, routes, and time scrubber stay in that project until a later decision pulls them in.
5. **Slice 1 implements the model in [story-bible.md](story-bible.md).** Story framing is stored on the story, ids are readable and frozen, and dangling references are refused. Intimacy replay, signals, and derived ranks are out. A belief is a Property or an Assertion.
6. **There is no Event-link record.** A cause, an order, or any other relationship between Events is an Assertion that names those Events. Story time is the span list on an Event. Version 2's `follows`, `directly_follows`, `depends_on`, and `during` are not a vocabulary in this model.
7. **Each user has their own model configs.** They are separate from that user's stories and are not part of a story export. The user provides their own OpenRouter API key through the UI. The key is not a field on a config and is not included in a config export or a story export.
8. **Local structured data is SQLite. Hosted structured data is Postgres.** Object storage is for blobs once they exist. Callers use the store interfaces. A JSON file under a process lock is not the slice 1 design.
9. **A conversation is a LangGraph thread with an owned row for one user and one story.** The chat agent's checkpointer holds the transcript; the row is the scope. A thread has one invoke in flight. It is not a Story Bible record, and it is not in the story export. The store allows more than one conversation per story.
10. **The user's API key is in the secrets store.** It is not in the config document, a story export, a config export, or the call log. On Railway the application encrypts it before writing.
11. **Call-log retention does not delete a record an evaluation run cites.** The local log has no cap. On Railway, uncited records older than 90 days may be deleted.
12. **The arc agent writes Story Bible records directly.** There is no intermediate plan and no conversion step. The chat transcript is the explanation.
13. **The planning unit is the story the conversation belongs to.** One description produces the framing and a small set of arcs. Later prompts revise that story. A beat, a scene, a sequence, or a graph window is not a mode of the first workflow.
14. **Candidate explorations and character interviews wait.** They are not part of the arc chat. When they are added, a candidate is not canon until it is adopted, and a character query is a read whose answer is not stored.
15. **An evaluation run is the comparison, and it cites the call log.** The run stores the fixture, the workflow version, the resolved model, the bible before and after, the checks, and any scores with their rubric version. Tokens, cost, and latency are read from the cited call records. A prompt change is a new workflow version. A runner writes that record. A library may replace the runner only if it stores the same record and still cites the call log.
16. **An evaluation runs deterministic checks and a model judge.** The checks cover tool-call validity and id handling, and they call no model. The judge scores the quality dimensions a check cannot.
17. **An evaluation records cost in total and per step.** There is no budget, and a cost does not fail a run.
18. **Evaluations do not run in CI.** The user launches a fixture and reads the comparison.
19. **The debug log records tool results.** A `tool_call` record carries the tool name, the arguments, the result or error, the duration, and the model call that requested it. The evaluation checks read those records. A tool record is kept when that model call is cited.
20. **The judge uses three dimensions per category, scored from 1 to 5.** Arcs, Story Bible construction, and later scenes each have their own three. Reasons are stored with the scores. There is no pass line and no single literary-quality score. The suite is five arc fixtures and five bible fixtures, with five scene fixtures when prose exists. A pairwise comparison is optional.
21. **The frontend is React and TypeScript, built by Vite, with Mantine for its components.** It lives in `frontend/` with its own `package.json`, managed with npm, and it builds to static files the service serves from its own port, so the local app stays one process. In development the Vite dev server proxies `/api` to the service, so the browser sees one origin either way and the service sends no CORS headers. The request and response types are generated from the service's OpenAPI document, not written by hand. A frontend step passes its type check, its lint, and its build, and has Vitest tests for logic that does not render, such as laying spans out in story time; a screen is checked by using it. Svelte and Vue would each have met the requirements; React was chosen because it has the widest choice of libraries for what the later slices draw. A framework that runs its own server, such as Next.js, was set aside because the service already serves the frontend, and a second server would make the local app two processes. A component library was chosen over Tailwind with copied-in components and over plain CSS because the UI is supporting work in this project: the editors need id pickers, dialogs, and refusal and conflict notices, and building those by hand is effort the project spends elsewhere. This item does not choose the widget that draws the two pictures; that stays with question 22. [architecture/application.md](architecture/application.md) states the build.
23. **There is no review gate before a commit.** An agent's writes land as they succeed, and the writer reviews them afterward: the history view shows what a turn changed, record by record with the before and after, and offers a revert of one commit or of the whole turn. That is the workflow this product aims at. A run is never held waiting for the writer to approve a batch, and no interrupt sits in front of a commit. The draft commit in [architecture/persistence.md](architecture/persistence.md) stays available as a mechanism for a later run whose writes must land together or not at all; using it does not add a wait, because the writer's review is the history and the revert either way. Approval on each write tool was already set aside in [architecture/agents.md](architecture/agents.md). A gate was considered because it is the stronger-feeling control, and set aside because it makes every agent turn block on the writer when the history already gives the writer the same power after the fact, without stopping the work. What the history view shows, and how the frontend presents a turn's diff, is part of question 22.
25. **The stream carries tool calls; the transcript may show them.** Item 40 puts `tool_call` and `tool_result` on the turn stream regardless, and the prompt-assembly rule is already met by the event types, so nothing architectural turns on whether the chat shows them. Whether and how the transcript renders them is a slice 3 rendering choice under question 22, and this list does not carry it as a question.
34. **The application layer is a Python API, and the UI is a separate frontend that is a client of it.** The Python application is a service with an explicit contract: stories, records, commits, history and revert, export and import, conversations, the turn stream and its stop, configs, the API key, the call list, fixtures and runs. That service is the caller the subsystem docs name: it turns a request into a user id, resolves a conversation row and checks its owner, builds and invokes agents with the logging context and a minted `run_id`, streams the turn, delivers a stop to the running turn by a row that turn reads (item 39), and runs the evaluation runner, the heartbeat, and the retention routine. The frontend is built separately and speaks only that contract; it never opens a store or builds an agent. Locally the service and the frontend run on one machine with one implicit user. Hosted, the service is what Railway runs. Version 2's in-process Python UI is why: the framework owned the wire, and it got in the way of the visualizations and tied the application to one process. Which framework draws the frontend is settled in item 21. The API's own choices are settled in items 39–41; the authentication mechanism, question 33, is the one still open. [architecture/application.md](architecture/application.md) is the doc that states them.
35. **A revision belongs to a record, not to the story.** The story store holds a row per record with its own revision. A commit saves a changeset guarded by those revisions, the store checks names inside the transaction, and the commit guards the unit tree and span chains where a rule depends on another record staying put. Unrelated parallel writes never conflict. A tool reruns a conflicting commit a bounded number of times, then returns the conflict as an error.
36. **Every commit leaves a history record with before-images.** The record carries the source, the conversation and turn for an agent's commit, and each change with the fields before and after. A revert is a commit that applies the inverses, guarded like any other, and the agent has no revert tool. The history is deleted with the story and is not in the export.
37. **A story-time timestamp is an ISO 8601 date or date-time.** Proleptic Gregorian, no time zone, years `0001` to `9999`, compared chronologically, a date-only value being the start of its day. The calendar is nominal, so a world without a Gregorian calendar still uses it. A generic integer timeline was considered and set aside as more than this version needs.
39. **A chat turn is a job the service owns.** Starting a turn writes a turn row: the conversation, a status of `running` and then `success`, `error`, or `cancelled`, the `instance_id` of the process running it, the `run_id` the caller minted, and the start and end times. The start returns the turn id in a response header and may also return the stream, whose first event is `started` carrying the same id, so the common case is one round trip; the frontend can drop that stream and subscribe to the turn id again, and the turn does not notice. The task runs in the service process that started it. A stop is a row write: the stop endpoint sets `stop_requested_at`, the running turn reads that row at each superstep boundary, holds back the pending tools, writes the tool results that say the turn was cancelled so the thread is valid for the next prompt, and only then sets the status to `cancelled`. The endpoint never writes `cancelled` itself; the status records what happened, not what was asked. The row is how a stop reaches the replica running the turn, with no routing. A turn whose instance has stopped beating is shown as interrupted under the heartbeat rule in [architecture/persistence.md](architecture/persistence.md), and its stored status stays `running`. The evaluation run in [architecture/evaluations.md](architecture/evaluations.md) is a sequence of these turns, so there is one run lifecycle. The turn row is durable; the task is not. Version 2's in-memory job manager, whose claims died with the process, is not what this is: nothing above the row is relied on for consistency, and the story is kept consistent by the commit alone. A held request, where the turn lives as long as the HTTP connection, was set aside because a refresh or a proxy timeout would end a long arc run that had already committed half its writes, with no way to re-attach. The event buffer a subscriber reads is in-process; fanning a stream across replicas is deferred with the rest of hosting, and a single replica is the hosted shape until then. This is the row a later resume (question 29) would reference; it does not implement one.
40. **The turn stream is a small set of typed events over SSE.** The subscribe endpoint for a turn id sends `started` (`turn_id`), `assistant_delta`, `tool_call` (name, arguments, `tool_call_id`), `tool_result` (`tool_call_id`, status, result or error), `commit` (`commit_id`, the ids of the records it changed, and the `tool_call_id` that produced it), `cancelled`, `error`, and `done`. The service consumes the LangGraph stream and emits those events; the frontend never sees a LangGraph message. A system message cannot reach the transcript because no event type carries one, which is the prompt-assembly rule enforced on the wire rather than in the frontend. The frontend renders `assistant_delta` as the reply. Whether it also shows `tool_call` and `tool_result` is a rendering choice, item 25. The `commit` event is why typed events were chosen over assistant text alone: the writer edits the same bible while the agent runs, and the frontend has to learn which records moved without polling the story. The write tool already has the commit id when it returns, so the event costs nothing to produce. `tool_call` and `tool_result` carry the same fields the call log's `tool_call` record stores, so the live transcript and the debug view agree. Each event has a sequence number within the turn; the service keeps the turn's events in an in-process buffer while the turn runs, and a subscriber that reconnects sends the last sequence it saw as `Last-Event-ID` and receives the rest. That buffer is the one item 39 names, and it is not durable. Forwarding LangGraph's own stream modes was set aside because it would put the filter in the frontend, against LangGraph's message shapes, which is how version 2 rendered a system prompt as assistant text. SSE was chosen over a WebSocket because the stream is one-way, the stop is its own request, resume is built into the protocol, and no connection upgrade is needed through a proxy. The note about what the writer has open is a content block on the user message and travels on the request that starts the turn, not on the stream.
41. **The background routines run in the service process, locally and hosted.** The heartbeat loop, the retention routine, the chat turn task, and the evaluation runner all start from the API's lifespan or from a request on it, as tasks on the same event loop. There is one kind of process and one `instance_id`. The evaluation runner is the turn task called once per fixture message, with the checks and the judge after. Retention is safe to run from more than one replica at once, which it already is: one idempotent delete that excludes the cited ids. A separate worker, with a queue such as Celery and the stream served from the database, was considered and set aside. Nothing the early slices run is heavy; model calls are I/O, and the checks and the bible copies are small. The robustness a worker buys, retries and a durable task owner, is not what the early slices need, and item 39 already accepts that a task dies with its process while the row says so. A worker would also move the in-process stream buffer in item 40 out of process at once, which is the hosting work item 39 deferred. Keeping one process is also what keeps the local install one command. The condition for revisiting is question 29: if a workflow must resume after a restart, a durable task owner is worth having, and the stream buffer moves out of process with it.
42. **A time point that names an Event can say which end of that Event it means.** The Event form of a time point is `{ event_id }` or `{ event_id, edge }`, where `edge` is `start` or `end`. With no `edge`, the `start` of a range means the Event's end and the `end` of a range means the Event's start, so a range from one Event to another runs from the end of the first to the start of the second, which is the common case. An `at` span that names an Event must give an `edge`, and a save without one is refused. The start and the end of an Event come from its single span. This replaces the earlier wording, "the bound in use", which did not say which bound of a period was meant. A fixed reading was considered in three forms: always the Event's end, always its start, and the bound of the same name. Each was set aside as the whole rule because no fixed reading fits every sentence a writer means, so the record can say it. Requiring `edge` on every time point that names an Event was set aside because most Events a span names are single moments, where it changes nothing, and the position already gives the common reading. Leaving a period unusable as a time point was set aside because the Story Bible doc's own example uses one. The story document's `schema_version` stays `1`: no story has been stored or exported under the earlier shape, so there is nothing to tell apart. [story-bible.md](story-bible.md) states the rule, and step 2 of slice 2 in [build-sequence.md](build-sequence.md) builds it.
43. **The service resolves story time, and the frontend lays the result out.** The Story Bible layer resolves each Event's spans to timestamps by the rules in [story-bible.md](story-bible.md), and `GET /stories/{story_id}/event-times` returns the result. The timeline draws from it and does not resolve a time point itself. The in-force view is computed in the service the same way when the entities view is built. Arranging the resolved times on the screen, the moments, the lanes, and the spacing, is frontend logic with Vitest tests, which is what item 21 means by laying spans out in story time. The reason is the agent. The owner wants an agent to be able to reason about when Events happen and where a new one could go, as the writer does on the timeline, and an agent cannot use a screen; the slice 3 read tools return what the service computed. Resolving in the frontend was set aside because slice 3 would then write the same rules a second time in Python, and the two could drift. What an agent's read returns beyond the resolved times, such as what is in progress at a time, is designed in slice 3 in [architecture/agents.md](architecture/agents.md).

## Slice 2

22. **How is each screen drawn?** Which views slice 2 builds is decided, and [ui.md](ui.md) states it: the records view, the timeline, the entities view, and the graph, each built read-only before any editing, then Arcs laid over the Events with the Arc editor, and the history. The timeline and the Arcs over it are the two pictures [story-bible.md](story-bible.md) requires. The entities view and the graph are the extra views this question said to confirm before building, and the owner confirmed them. A view beyond that set is added to [ui.md](ui.md) first. [architecture/persistence.md](architecture/persistence.md) requires a history view: the story's commits, what each changed, and a revert action, grouped by turn once the agent exists. Once the agent exists, the frontend also shows a turn's status from its row in item 39: running, cancelled, or interrupted under the heartbeat rule; and item 23 makes the history view, with a turn's diff and its revert, the writer's review of what the agent did, so that view is not optional. What stays open is how each of these is drawn. The widget for a view is chosen in that view's doc under `ui/` when its step starts, and what the history and a turn's diff look like is decided at their steps. Whether the transcript renders tool calls (item 25) is a slice 3 choice, not part of this question. Whether the story list separates an evaluation run's story from stories the writer started by hand is decided here, once slice 4 creates such stories. Slice 2 of [build-sequence.md](build-sequence.md) is where the slice 2 part is closed, one view at a time.

[architecture/agents.md](architecture/agents.md) leaves the list to the frontend, over the conversations endpoint in [architecture/application.md](architecture/application.md).
## If slice 1 needs a narrower reading of story time

26. **Does a stricter overlap rule replace the in-force view?** [story-bible.md](story-bible.md) already defines the slice 1 reading. An empty `when` is included at every query point. A `range` with no `end` still applies after its `start`. Separate ranges do not fill the gaps between them. An `at` span does not put a statement in force. An unresolved comparison is marked and the statement is still included. Two statements that contradict both save; nothing detects the contradiction. A later rule may tighten that view. It must not add a record type or a field beside `when`. Revise the in-force section of [story-bible.md](story-bible.md) when a story needs the tighter rule.

## Later

27. **Do statements gain a marker for objective fact, belief, or plan?** Slice 1 has no such marker. A belief is a Property or an Assertion. Adding a marker later must not block a writer's edit. Close this in [story-bible.md](story-bible.md) if a story needs the distinction.
28. **Do Assertion references need roles, and should Properties ever link to other Properties?** Slice 1 does neither, and a change does not propagate on its own. Close this in [story-bible.md](story-bible.md) if that becomes necessary.
38. **Does a story ever need its own calendar?** Item 37 fixes the timestamp as an ISO 8601 value in a nominal Gregorian calendar. A story with its own month names and lengths, or years outside `0001`–`9999`, would get a new kind of time point beside the timestamp and the Event id, inside the existing `when` list. No record gains a field. Close this in [story-bible.md](story-bible.md) if a story needs it.
29. **When does a workflow need to survive a process restart?** [architecture/persistence.md](architecture/persistence.md) says an early run lives in the process, and the durable artifact is the last successful story transaction. Item 39 gives a turn a durable row and a non-durable task, and item 41 keeps the task in the service process; a resume would be built on that row, and it is the condition under which a worker becomes worth having. Checkpoint, resume, and a run that must continue after a crash stay open. The persistence doc and [architecture/application.md](architecture/application.md) revise this when that is needed.
30. **Field-level authority for locations**, once Story Space is integrated. Stays deferred with that project.
32. **How many candidates, and what may a character query know?** [architecture/agents.md](architecture/agents.md) says both wait, that a candidate is not canon until it is adopted, and that a character query is an unstored read. How many directions, how they are produced and ranked, whether exploration runs only when asked, and the exact knowledge boundary stay open. That doc closes them when the features are designed.
44. **Can an Event's time be recorded more loosely than a span allows?** A `when` list can say that an Event happens at a moment, at several moments, or across a period whose bounds may be unknown, and an empty list says no time was recorded. It cannot say that an Event happens once at some unknown moment inside a window, because a `range` is a period the Event lasts for. It cannot say that an Event comes before or after another without giving a time; an Assertion can state that order, and nothing reads an Assertion as story time. The owner wants both eventually. Each would be a new kind of span in the `when` list, which [story-bible.md](story-bible.md) already allows without a new field on any record. Until then the timeline draws only what the model stores. Close this in [story-bible.md](story-bible.md) when a story needs it.
33. **How does a hosted request authenticate as a user?** [architecture/persistence.md](architecture/persistence.md) requires a user id on every store call and makes ownership an authorization check. Settled item 34 fixes where that happens: the API resolves every request to a user id before any store or agent is touched, and locally that resolution returns the one implicit user. The mechanism a hosted deployment uses to prove who the request is from stays open, as an adapter behind that step. [architecture/application.md](architecture/application.md) records the step now and the mechanism when hosting is built.
