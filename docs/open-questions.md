# Open questions

These are the decisions the proof of concept in [build-sequence.md](build-sequence.md) still has to make. Each one names the doc that will close it.

A decision that has been made is not kept here. It is stated in the doc that owns its area, with the reason where the reason matters, and the question is removed from this list. [architecture.md](architecture.md) maps each part of the system to its doc.

A decision that can wait until after the proof of concept is not kept here either. It is in [future-work.md](future-work.md), with the work it belongs to.

The other docs name a question by its number in this list. When a question is removed and the numbers after it change, the references change with them.

## Story time

1. **Can an Event be recorded as coming before or after another, with no time given?** A `when` list can place an Event at a timestamp, or at the start or the end of another Event. The second is exact: it says the Event happens at the moment the other one ends, not some time after it. An Assertion can state an order, and nothing reads an Assertion as story time. An Arc's `event_ids` hold the thread's own order, which is not story time either. This matters for the arc-planning agent. A description rarely gives dates, and the agent is told not to invent a fact, so an Event it writes is likely to have an empty `when`, and the timeline cannot place it. There are two ways to close this. One is a new kind of span in the `when` list, which [story-bible.md](story-bible.md) allows without a new field on any record. The other is no change to the model: the base prompt tells the agent to use a timestamp or the edge of another Event when the description supports it, and to leave the time empty otherwise. The owner wants the looser record eventually. Close this in [story-bible.md](story-bible.md), and in [architecture/agents.md](architecture/agents.md) for the base prompt, before the agent's base prompt and tools are designed.

## The arc-planning agent

2. **Which LangChain integration reaches OpenRouter?** [architecture/model-configuration.md](architecture/model-configuration.md) says a binding builds the chat model from a config and nothing else does. It does not say which chat model class that is. The candidates are a chat model made for OpenRouter, and the OpenAI-compatible chat model pointed at OpenRouter's endpoint. The choice has to carry what the docs already require: `reasoning_effort` sent as OpenRouter's unified `reasoning.effort`, tool calls, a structured `response_format`, streaming on the async path, and token usage on the assistant message's `usage_metadata`, with the cached-input count when the provider gives one, because the call log and the evaluations read it. Close this in the tech stack in `AGENTS.md` and in the model-configuration doc, before the binding is built.
3. **Does a model call retry, and with what settings?** [architecture/llm-debug-logging.md](architecture/llm-debug-logging.md) says a retry middleware is listed before the logging middleware, so each attempt has its own record, and that the agents doc chooses the settings. [architecture/agents.md](architecture/agents.md) does not choose them. It says only that the tools do not use retry middleware. Open: whether the shared builder lists a model retry middleware at all, how many attempts it makes, which errors it retries, how long it waits between them, and what the turn gets after the last attempt: the synthetic assistant message LangChain returns by default, or an error that ends the turn. Each attempt is a call in the log and in an evaluation's usage. Close this in the agents doc before the shared builder's middleware list is built.
4. **How long may a conversation thread grow?** Nothing trims or summarizes a thread. Each turn sends the whole conversation to the model, with its tool calls and their results, so a turn's input grows with every turn before it. For now the reset is a new conversation, which [architecture/agents.md](architecture/agents.md) gives the writer. The bible carries the story's state, so a new conversation loses the dialogue and not the work. Open: whether that is enough, or whether a long thread is trimmed, summarized, or stripped of old tool results, and whether the writer is told when a thread is long. An evaluation run starts on a new conversation, so the runs do not show this. The input tokens of each turn in the call log do. Close this in the agents doc, and in [architecture/prompt-assembly.md](architecture/prompt-assembly.md) if a turn's messages are rewritten, once the chat has been used on a long conversation.
