# LLM debug logging

This is how every model call is recorded, and how that record stays the prompt and response the model actually saw. The model-configuration doc owns the prefix middleware. The prompt-assembly doc owns which layer a piece of context belongs in. This doc owns the tap and the record. An evaluation run cites these records. It does not capture prompts a second way.

## The tap

Every model call is an agent from `create_agent`, including a one-shot call inside a workflow. The shared agent builder passes one middleware list. The prefix middleware is first. The logging middleware is last, so it is innermost and wraps only the provider call.

A node does not opt in. A later workflow is logged because it builds its agents the same way.

The middleware is a class with both `wrap_model_call` and `awrap_model_call`. LangChain does not fall back from one to the other: a middleware with only the sync hook raises `NotImplementedError` when the agent runs under `ainvoke` or `astream`, and the reverse. The chat UI streams, so the async hook is the one that runs most. The prefix middleware has the same requirement, and the model-configuration doc states it.

The logger is one function around the handler:

1. Write a record with status `running`.
2. Call the handler.
3. Update that record to `success` or `error`.

There is no separate start event and finish event. A finish cannot arrive without a start, and a start cannot be left waiting for a finish that took another path. The one remaining gap is the process dying mid-call. That leaves the stored status at `running`. The view, below, is what presents those.

A retry middleware is listed before the logging middleware. Each attempt then calls the logger, and each attempt gets its own record, with its own error and duration. A logger outside the retry would fold the attempts into one record and drop the intermediate errors. LangChain's `ModelRetryMiddleware` defaults to `on_failure="continue"`, which returns a synthetic assistant message carrying the error text after the last attempt. That message is made outside the logger and is never a record. The log shows the attempts; the transcript shows the message. The agents doc chooses the retry settings.

A fallback middleware, if one is ever listed, swaps `request.model` before the logger sees it. The record therefore stores the model the request names, not only the model the config names. See [The record](#the-record).

Streaming has no second path. The handler returns the complete assistant message after the stream finishes. Tokens reach the frontend as the typed events the service emits from the LangGraph stream, as the application doc defines them, not through this middleware. Version 2 logged both the streaming and one-shot entry points of a chat-model subclass. That split is gone.

Store calls are wrapped so they cannot raise. If writing the `running` record fails, the handler still runs. If updating the record fails, the model's result is still returned, and the model's exception is still re-raised unchanged. A logging failure must not fail the call, and it must not replace the model's error with a store error. In the async hook the store is awaited, not called through a blocking lock. A blocking write inside the async hook would stall every agent sharing the event loop.

## What is recorded

The record is the `ModelRequest` the logging middleware receives, and the response the handler returns. That request already carries the prefix and the node's base prompt on `system_message`, and its `messages` are the messages for this call after any override. Logging the conversation's stored message list would miss the system message and anything added only on the request. The prompt-assembly doc is the authority for those layers. This doc's promise to it: the stored prompt is that request.

### Identity

Four ids, each with one job:

| Field | Source | Role |
| --- | --- | --- |
| `call_id` | Generated by the middleware for this attempt | The record's key. |
| `run_id` | `runtime.execution_info`, set by the caller | The agent run. Every model call in one agent invoke shares it. |
| `thread_id` | `runtime.execution_info` | The conversation. Empty for an agent run without a thread. |
| `workflow_run_id` | `runtime.context`, set by the caller | One run of a workflow, across every agent it invokes. |

`runtime.execution_info` is available to middleware hooks and to tools from `langgraph` 1.1.5. Its `thread_id` is the checkpointer's thread, and is `None` for an agent run without one. Its `run_id` is the value the caller put in the invoke `config`, and is `None` otherwise; LangGraph does not mint one. So the application layer mints a `run_id` for every invoke and passes it in `config`, the same way it passes `thread_id`. The write tools in the agents doc read the same two values from their `ToolRuntime` to stamp the commit record, so a turn's call records and its commits carry the same `run_id`.

`run_id` is not the record key. Version 2 keyed the log on the callback run id, which was one id per call and could not group the calls of one agent turn. Using the agent run id as the key would collide when one turn makes several calls, and when a retry makes several attempts.

`run_id` is also not the workflow run. LangChain gives a child runnable its own run id, so a one-shot agent nested in a workflow node reports its own run, not the workflow's. An evaluation that wants every call from one workflow run reads `workflow_run_id`, which the caller mints when it starts the run and passes in the context. For the chat agent, where the agent is the run, the caller can leave it empty.

### Attribution

Attribution is passed in, not scraped from the graph. With a one-shot agent nested inside a workflow, the innermost `langgraph_node` is the agent's own `model` node, and the outer step's name is buried in the checkpoint namespace.

The shared agent builder passes a context object, `context_schema`, and the logger reads `request.runtime.context`:

| Field | Role |
| --- | --- |
| `user_id` | The user whose call this is. The log is scoped by it; see [The store](#the-store). |
| `story_id` | The story this call is working on. |
| `workflow` | The workflow, or `chat` for the arc-planning conversation. |
| `workflow_run_id` | One run of that workflow, as above. |
| `node_id` | The registry id from [model-configuration.md](model-configuration.md). This is the key an evaluation run filters on. |
| `config_id` | The model config that was resolved for that node. |

A missing field is stored empty, except `user_id`. The agent builder requires it, because a record without an owner cannot be scoped. The logger does not fill any field from node metadata.

### The record

`kind` is `model_call` or `tool_call`. [Tool results](#tool-results) is the second kind.

| Field | Role |
| --- | --- |
| `call_id`, `run_id`, `thread_id`, `workflow_run_id` | Identity, as above. |
| `kind` | `model_call`. |
| `status` | `running`, then `success` or `error`. |
| `started_at`, `finished_at` | ISO timestamps. `finished_at` is empty while `running`. |
| `duration_ms` | Wall-clock time from just before the handler call to the handler's return or exception. Empty while `running`. |
| `instance_id` | The process or replica that made the call. [The view](#the-view) uses it to tell an interrupted call from one still in flight. |
| `user_id`, `story_id`, `workflow`, `node_id`, `config_id` | The context fields. |
| `config_model` | The model id on the resolved config. |
| `model` | The model id the request names, read from `request.model`. Equal to `config_model` unless a fallback middleware swapped the model. |
| `temperature`, `max_tokens`, `reasoning_effort` | The config's sampling options. Empty when the config omits them. |
| `model_settings` | `request.model_settings`, after secret scrubbing. Empty when the request has none. |
| `tools` | Names of the tools offered on this call. A provider-side tool given as a dict is recorded by its `type`. |
| `response_schema` | Name of the schema when `response_format` is set. Empty otherwise. |
| `prompt_messages` | The request as structured messages: the system message, then each message. |
| `response_text` | The text of the assistant message in `ModelResponse.result`. Empty on error. |
| `response_tool_calls` | Tool calls the model requested: `name`, `args`, `id`. Kept when the tool later fails. |
| `structured_response` | The parsed object for a structured one-shot. Empty when there is none. |
| `response_metadata` | Provider metadata, including token usage, after secret scrubbing. |
| `error` | The exception text. Empty on success. |

A structured message has `role`, `content`, and, when present, `tool_calls` (`name`, `args`, `id`), `name`, and `tool_call_id`. The system message is included. Its content is the prefixed system message: the prefix block, then the base prompt's blocks. Plain text is stored as text. Block content is stored as the blocks. There is no separate text copy of the prompt. The view renders text from the structured messages, so one request is stored once. Version 2 stored both, with the text as a fallback, and doubled the record.

`ModelResponse.result` is a list. It usually holds one assistant message, and it can also hold a tool message when the provider used a tool call to produce structured output. `response_text` and `response_tool_calls` come from the assistant message.

### Secrets

Before `response_metadata` or `model_settings` is written, dictionary keys are scrubbed recursively, including keys nested in objects and lists. A key is redacted when, compared case-insensitively, it is one of `api_key`, `apikey`, `authorization`, `access_token`, `auth_token`, `secret`, `client_secret`, or ends in `_api_key`, `_secret`, or `_token`. The value is replaced with `[redacted]`. Text inside the prompt and the response is not scrubbed. A story can use those words.

Version 2 redacted any key containing `token`. Applied to `response_metadata`, that rule would redact `token_usage`, `prompt_tokens`, and `completion_tokens`, which are the usage numbers [The view](#the-view) falls back to. Match whole key names, not substrings.

The config fields copied onto the record are the model id and the sampling options. They do not contain the API key. The scrub is a safety net for metadata that arrives from the provider.

## The store

Call logs are debug data for the user who made the calls. They are not part of a story, and they are not in a story export. They follow the same boundary as that user's model configs: one user's prompts are not another user's log. Every record carries `user_id`, and every read is scoped by it.

The middleware and the view talk to a call-log store through one interface. Nothing else opens whatever is behind it. The persistence doc chooses what is behind it, locally and on the hosted deployment, together with the story store and the config store. This doc fixes the interface and the properties an implementation has to keep.

The interface:

| Operation | Role |
| --- | --- |
| `start(record)` | Insert a record keyed by `call_id`, with status `running`. |
| `finish(call_id, outcome)` | Update that record with the outcome fields: status, `finished_at`, `duration_ms`, response fields or error. |
| `get(user_id, call_id)` | One record. |
| `list(user_id, filters)` | Newest first. Filters are the attribution fields and the ids in [Identity](#identity). |

Each operation has a sync and an async form, because the middleware has both hooks.

The caller never reads the whole log to write one record. Two concurrent calls write two keys. Version 2's store loaded the full file, changed it, and wrote it back on every event, and parallel nodes tore that file on Windows until the whole cycle was put under one process lock. The lock treated the symptom. Keyed writes are the design: the store decides how two writes to different keys stay safe, and the middleware does not know.

Whatever store is used has these properties:

- Two records written at once both land. A record is never torn.
- A `finish` for a `call_id` the store has no `start` for still lands. The start write may have failed.
- A store call does not raise out of the middleware, and it does not block the async hook, as [The tap](#the-tap) says.
- A store that cannot read its own log recovers rather than failing every later call. Call logs are disposable. What recovery means is the implementation's.
- Reads are scoped by `user_id`.
- Retention is the store's policy, and it does not remove a record an evaluation run cites. An evaluation run keeps its results by `call_id`; a rolling cap that deleted cited records would hollow out those results. The persistence doc chooses the policy, and the evaluations doc states what a run needs kept. Neither a cap nor a count is fixed here.

## The view

The debug view is read-only. It lists calls newest-first, including failures and calls still `running`. It does not edit records.

A `running` record is shown as interrupted under the heartbeat rule in the persistence doc: the instance named by its `instance_id` has no recent heartbeat, or no heartbeat row at all. The API derives that on read, as the application doc says; the stored status stays `running`, and the view does not compare against its own process. The rule is per instance, not "earlier than process start", because the hosted deployment can run more than one process and the view may not be served by the one that made the call. Version 2 had no process-death case to show, because a missing finish was a separate event. Here the stored row is simply unfinished.

Prompt and response markup is shown literally. Version 2 rendered the prompt as Markdown, and tags such as `<canvas>` inside a prompt were executed. Escape the text before any rendering that would interpret markup.

Token counts prefer the assistant message's `usage_metadata`, and fall back to the provider usage field in `response_metadata`. The view shows input, output, reasoning, and total when those numbers are present.

The view can show the record's fields: status, times, duration, the attribution fields, the model and sampling options, the prompt by message, the response text, the requested tool calls, the structured response, the scrubbed metadata, and the error. The page layout is not specified. Version 2's NiceGUI debug page is not the view to copy.

## Tool results

Version 2 recorded the tool calls the model requested, and not what the tools returned. The evaluation checks read the result, so the log records it.

`wrap_tool_call` and `awrap_tool_call` sit in the same middleware list. The class implements both, for the same reason the logging middleware does. One record is written per tool invocation.

| Field | Role |
| --- | --- |
| `call_id` | This record's key. |
| `kind` | `tool_call`. |
| `parent_call_id` | The model call that requested it. |
| `tool_call_id` | The id the model gave this tool call, from the parent's `response_tool_calls`. The persistence doc's commit record names it, which is how a change in the story is joined to the call that made it. |
| `user_id` | Owner. Reads are scoped by it, as for a model call. |
| `status` | `success` or `error`. |
| `tool_name` | The tool that ran. |
| `arguments` | The arguments the tool received. |
| `result` | The tool's result. Empty on error. |
| `error` | The error text. Empty on success. |
| `duration_ms` | Wall-clock time of the tool invocation. |

A tool record is kept when its `parent_call_id` is a model call an evaluation run cites. The deletion routine in the persistence doc excludes those parents, and it excludes a tool record that points at one of them.

## What an evaluation run uses

An evaluation run stores the model-call `call_id`s it cites. It finds the tool records by `parent_call_id`. Prompts, responses, requested tool calls, token usage, and durations come from the model-call records. The tool name, arguments, result or error, and duration come from the tool records. The evaluations doc defines the run, the checks, and the scores. It does not define another capture path.
